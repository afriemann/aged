## Why

aged currently supports exactly one shared bearer token and one secrets tree. Anyone with the token can read, write, and list every secret. To use aged for more than one person (or more than one trust boundary on the same box), each identity needs its own token and a storage tree the others cannot reach — with zero chance of one token's requests ever resolving another token's secrets. Since the server is now a blind ciphertext store (no identity, no crypto — see the archived `client-side-encryption` change), this becomes purely a storage-isolation problem: no per-user identity provisioning, no server-side crypto migration tooling, none of the complexity the original (pre-client-side-encryption) draft of this proposal assumed.

## What Changes

- `aged serve` stops treating the top-level `token` config field as an implicit tenant. `Config.Token` itself is **not removed** — it remains the CLI client's own credential field, used by every client command (`get`/`set`/`list`/`delete`) exactly as today; only the server's interpretation of it changes.
- Server tenants come from a `[[users]]` array (`name` + `token` per entry), optionally combined with a single env-constructed entry: when both `AGED_TOKEN` and a new `AGED_USERNAME` are set, they define one additional user (preserving today's "start from environment variables alone, no config file" deployment path for the common single-user case).
- `secrets_dir` remains a shared, top-level config key — the base directory under which every user's storage lives — but is no longer itself a tenant's storage root. Each user's storage is `secrets_dir/<name>/`, uniformly, for every configured user (config-file-defined or env-defined). There is no implicit/default user and no special-cased root-of-secrets_dir tenant.
- Startup requires at least one user (from either source) and fails fast on: no users configured; duplicate tokens; duplicate names (case-insensitive, as defense-in-depth even though the deployment target is a case-sensitive filesystem); an invalid name (plain identifier, ASCII letters/digits/`.`/`_`/`-` only, not `.`/`..`, bounded length, not starting with `-`); a token that isn't a fixed expected length (closes an empty-token auth bypass and removes a length-based timing side-channel in the same move); or any pre-existing `.age` file (or non-directory entry) found directly under `secrets_dir` — this last check exists specifically to convert an operator forgetting to migrate existing secrets from a silent, fleet-wide 404 outage into a loud, pre-traffic startup failure naming the offending files.
- The bearer-auth middleware resolves the request's token against every configured user using constant-time comparison against each candidate (no early exit — a structural test, not a wall-clock timing test, asserts this), then routes the request to that user's own `Store` (rooted at `secrets_dir/<name>/`). `GET /secrets` returns only the authenticated caller's own names (an explicit, testable statement of the isolation goal).
- `aged rotate-token` gains an optional `<username>` argument: required when more than one user is configured (and lists the available names on error — this is not a new disclosure, since anyone invoking the command already has read access to the config file containing every name), auto-selected when there is exactly one. It rotates that user's token in place; the whole resulting `[[users]]` block is validated (no duplicates, no empty fields) before the file is written, so a rotation can never produce a config that fails to start.
- `aged rotate-identity` gains a required `--user <name>` flag whenever more than one user is configured (it refuses to run ambiguously against the shared multi-tenant base otherwise); it operates against that user's `secrets_dir/<name>` subtree specifically, exactly as it operates against the whole `secrets_dir` today in the single-user case.

**BREAKING**: Yes.
- The top-level `token` config key no longer authenticates server requests on its own — every deployment (including a single-user one) must define at least one user, via `[[users]]` and/or the `AGED_TOKEN`+`AGED_USERNAME` env pair.
- Existing on-disk secrets living directly under `secrets_dir` (not in a subdirectory) are no longer served, and the server now refuses to start at all while any are present — they must be moved into `secrets_dir/<name>/` for whichever user should own them first. This is a filesystem move only (content is already opaque ciphertext; no crypto or identity is involved), but — since namespaced secrets already legitimately create subdirectories directly under `secrets_dir` today — it is not a single `mv`; design.md will specify the exact safe sequence.
- `aged rotate-token`'s invocation changes for any deployment with more than one user (a username argument becomes mandatory); unchanged for the common single-user case.
- `aged rotate-identity` requires `--user <name>` for any deployment with more than one user.
- `aged list`'s output becomes tenant-scoped: a client that previously saw every secret now sees only its own tenant's — a client-visible behavioural change, not just a server-internal one.

## Capabilities

### New Capabilities

(none — this modifies the existing `aged` capability)

### Modified Capabilities

- `aged`: replaces the single-tenant `HTTP Authentication`, `Secret Listing`, and `Environment Variable Configuration` requirements' single-token model with multi-tenant `[[users]]`/env-pair configuration, per-tenant storage isolation (with a tightened, symlink-aware path-containment check, since directory isolation is now a security boundary rather than only a traversal-prevention measure), startup validation (no users configured, duplicate tokens/names, invalid names, fixed-length token check, unmigrated-secrets detection), tenant-scoped listing, and username-aware `Token Rotation` and identity-rotation requirements.

## Impact

- **Code**: `cmd/aged/config.go` (schema: add `Users []UserConfig`, `AGED_USERNAME` env handling; `Token` field retained), `cmd/aged/server.go` (tenant resolution in `bearerMiddleware`/`serve`, per-tenant `Store` construction, startup validation, tightened `secretPath` containment check), `cmd/aged/rotate.go` (`rotateToken` gains a username parameter and TOML array-of-tables read/validate/write logic), `cmd/aged/rotate_identity.go` (`--user` flag, scoped `secrets_dir/<name>`), `cmd/aged/main.go` (CLI arg wiring for both commands, updated help text and env var documentation).
- **Config**: `[[users]]` array and `AGED_USERNAME` are new; `token`/`secrets_dir` keys unchanged in shape, but the server's use of `token` changes as described above.
- **Deployment**: no `aged.service` changes. Existing deployments (e.g. the production homebox instance) must update their config to `[[users]]` (or the env pair) and move existing secrets into a named subdirectory before upgrading; the server's own unmigrated-secrets startup check makes a missed step a loud failure rather than a silent outage.
- **Explicitly accepted limitations** (documented, not solved, by this change): isolation is application-layer only, with no OS-level (uid/gid/chmod) backstop between tenants' directories, and provides no confidentiality-from-operator beyond what client-side encryption already provides; revoking or adding a user requires a config change and a full service restart, interrupting every other tenant; a removed user's directory is orphaned on disk indefinitely; there are no per-user quotas or rate limits (shared upload-size limit, shared disk); the name-binding envelope binds secret name but not tenant identity, so a secret misfiled into the wrong tenant's tree is caught only when that tenant holds a different age identity than the correct owner (README will recommend distinct identities per tenant); the number of configured users is not secret and the timing-safety claim is scoped accordingly (equal-length-token comparison prevents distinguishing *which* user matched or *whether* one matched, not *how many* are configured).
- **Out of scope**: any command for renaming/moving a user's storage tree (still a plain `mv`, not a dedicated feature); multi-recipient/shared-secret access between users; hot-reload of the user list without a restart; per-user audit-log identification beyond adding the resolved username to the existing `auth ok:` success line (the pinned `auth failure:` line's format is unchanged, to avoid touching the fail2ban-consumed contract on the one line it actually matches).
