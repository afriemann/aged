## Why

aged's server currently holds the age identity (private key) used to encrypt and decrypt every secret. That means the service operator can decrypt any stored secret regardless of storage isolation — trust is placed entirely in the operator, not in the cryptography. Moving encryption and decryption to the client removes that: the server becomes a blind ciphertext store that never possesses any private key material, so the operator cannot read secret *values* even with full filesystem and API access. Doing this now, while there is exactly one user and one secrets tree, is the cheapest point to migrate — a future multi-user change can then build on a server that never needs to provision or hold per-user identities at all.

This change gives **confidentiality**, not integrity or authenticity: age encryption has no built-in binding between a ciphertext and the name it is stored under, so without a mitigation an operator with raw filesystem access could still swap, roll back, or forge a secret under an existing name. This proposal includes a cheap mitigation for that (see below) rather than leaving it as a silent gap. Metadata (secret names, approximate value size, access timestamps, the existing `auth ok:`/`auth failure:` log lines) remains visible to the operator — that is an accepted, explicitly documented limitation, not something this change attempts to hide.

## What Changes

- `aged set <name>` now encrypts the value locally (client-side) using the caller's own age identity before uploading; the server receives and stores ciphertext bytes only. The plaintext is prefixed with a small header binding it to its secret name (e.g. `name: <name>\n\n<value>`) before encryption, so a ciphertext file swapped or renamed on disk fails a name-match check on retrieval instead of being silently returned under the wrong name.
- `aged get <name>` now downloads the stored ciphertext and decrypts it locally, trying every identity found in the caller's identity file (supports an overlap window during identity rotation) and verifying the decrypted plaintext's bound name matches the requested name before returning it. stdout behaviour (plaintext, no trailing newline) is unchanged for chezmoi compatibility.
- The server's `Store` no longer holds or reads any age identity. `setValue` validates that uploaded bytes begin with the fixed age v1 file magic (`age-encryption.org/v1\n`, verified against `filippo.io/age@v1.2.1`'s own header-parsing constant) — a plain byte-prefix check, not a decrypt attempt, so the server never constructs or holds any identity, real or otherwise — and rejects anything else with HTTP 400. `getValue` returns the stored bytes verbatim. Both the upload and download paths are fully binary-safe (`[]byte` throughout); no trimming is applied to ciphertext anywhere in the server or the transport client — the one authorised plaintext trim happens exactly once, client-side, before encryption.
- The upload size limit switches from a silently-truncating `io.LimitReader` to `http.MaxBytesReader`, so an oversized body is rejected with an error instead of being truncated into a corrupt-but-plausible-looking stored file.
- `GET /pubkey` is **removed** from the HTTP API (the server has no key to report). `aged pubkey` becomes a local command: it reads the caller's own identity file and prints its recipient — no network call.
- `aged serve` no longer reads `identity`/`AGED_IDENTITY` to operate, but if either is still configured at startup it logs a clear warning naming the file and explaining it is unused and should be secured/removed once migration is verified — closing the gap where a stale config setting looks harmless but is actually a live, forgotten private key.
- `aged init` is unchanged in behaviour, but is now documented and used as a client-side operation (run on each machine that will call `get`/`set`, not on the server host). Machines that need access to the same secrets share the same identity file, copied and protected exactly as the bearer token already is today (per the existing README guidance) — this change does not add multi-recipient/multiple-identity encryption; that is an explicit non-goal for now.
- New `aged rotate-identity <new-identity-file>` command (repeatable — used for the initial migration and for any future identity rotation): reads every secret under the currently configured `secrets_dir`, decrypts each with the currently configured `identity`, re-encrypts it to the new identity's recipient, and writes the result into a staging directory. Every staged secret is then decrypted with the new identity and compared against the originally captured plaintext before anything real is touched. Only if every secret verifies does the command perform the swap: the old `secrets_dir` is renamed to a timestamped backup (`secrets.old-<timestamp>/`) and the staging directory takes its place. The command refuses to run if it detects the server's configured address is already listening (a proxy for "stop `aged serve` before rotating"), supports `--dry-run` (decrypt/re-encrypt/verify only, writing nothing), and never prints decrypted plaintext or any private key material.

**BREAKING**: Yes.
- Wire format: `POST`/`GET /secrets/{name}` now carry ciphertext, not plaintext. A client and server must be upgraded together; an old client talking to a new server will have its plaintext upload rejected by the magic-prefix check (400), and a new client talking to an old server will fail to decrypt a plaintext body — both fail loudly rather than silently leaking or corrupting data.
- `GET /pubkey` HTTP endpoint is removed.
- `aged serve` no longer requires `identity`/`AGED_IDENTITY` to start; any deployment relying on the server holding/auto-managing the identity file must migrate first (see `rotate-identity` above) before the old identity file is discarded.
- Multi-machine access changes shape: today one bearer token unlocks decryption from any machine (the server decrypts). After this change, only a machine holding the matching identity file can decrypt — the identity file must be copied to every machine you run `get`/`set` from, the same way the bearer token is already distributed today.

## Capabilities

### New Capabilities

(none — this modifies the existing `aged` capability)

### Modified Capabilities

- `aged`: rewrites the Secret Storage and Secret Retrieval requirements to describe server-side opaque-ciphertext handling (magic-prefix validation only, no decrypt) instead of server-side encrypt/decrypt; removes the Public Key Endpoint requirement (HTTP); adds requirements for client-side encryption/decryption (including the name-binding integrity check and multi-identity decrypt), server-side ciphertext format validation, the `rotate-identity` command, and the stale-identity startup warning. Identity Initialisation requirement is retained with clarified client-side scope. Environment Variable Configuration requirement is updated to reflect `identity`/`AGED_IDENTITY` as client-only.

## Impact

- **Code**: `cmd/aged/server.go` (`Store` loses identity/crypto entirely, gains magic-prefix validation and `http.MaxBytesReader`; HTTP handlers for `/pubkey` removed; `/secrets/{name}` handlers become fully binary-safe passthrough), `cmd/aged/client.go` (`get`/`set`/`pubkey` gain local age crypto including name-binding and multi-identity decrypt; the string-trimming `request()` helper is replaced with a byte-safe variant for `get`/`set`), new `cmd/aged/rotate_identity.go` (the `rotate-identity` command: stage → verify → swap, dry-run support, running-server detection), `cmd/aged/main.go` (command wiring, updated help text), `README.md` (server setup no longer generates/holds an identity; client setup now includes `aged init`; migration runbook for the existing deployment; explicit guidance not to point a client's `identity` at the server's old identity path).
- **Config**: no schema changes; `identity`/`AGED_IDENTITY` is retained as a key but its consumer changes from server to client, with a startup warning if it's still set for `aged serve`.
- **Deployment**: `aged.service` needs no sandboxing changes, but its setup instructions change — the server no longer runs `aged init` against `/var/lib/aged`. The migration runbook requires stopping the service for the duration of `rotate-identity`.
- **Forward compatibility with multi-user-support (paused change)**: once this lands, adding a user is purely "a new token + a new storage subdirectory" — no per-user identity provisioning or auto-generation is needed server-side, since the server never holds identities for anyone. The paused `multi-user-support` proposal's `migrate-user` command was designed as a server-side decrypt/re-encrypt across tenants — that is no longer possible once the server holds no identity, and it will need to be redesigned as a client-side operation when that change is revisited. Server-mediated secret *sharing* between two users (server re-encrypting one user's secret for another) also becomes impossible; multi-user-support does not currently plan any sharing feature, so this is recorded as an accepted, silent-until-now constraint rather than a scope change.
- **Out of scope**: multi-user support itself (tracked separately, currently paused); any change to the `chezmoi` integration contract (unaffected — `aged get` still prints plaintext to stdout); multi-recipient encryption (multiple distinct identities decrypting the same secret) — the single-identity-copied-per-machine model is the accepted default for now; a signature/MAC scheme for full write-authenticity (the name-binding header defends against accidental/malicious file swaps, not against an operator who deliberately forges a plausible new ciphertext for a name — that residual is accepted and documented in the spec, not solved here).
